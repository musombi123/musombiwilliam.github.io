Six-month learning path: Digital Forensics & Reverse Engineering

This is a self-study programme, not an accredited qualification. A realistic target is 8–12 focused hours per week; extend the schedule when a topic needs more time.

Month 1 · Foundations

Linux and Windows architecture, permissions, processes, IP/DNS/TCP/TLS/HTTP, Python file and binary I/O, Git, C fundamentals and introductory x86-64/ARM64.

Practical: build a file inventory with SHA-256, summarize a training PCAP, and compare a self-compiled program's source and disassembly.

Month 2 · Storage and acquisition

Partitions, volumes, sectors, FAT/exFAT, NTFS, ext4, file metadata, deleted entries, imaging, write blockers, bad sectors and acquisition logs.

Practical: use a disposable lab image, hash it, identify partitions and document acquisition limits.

Month 3 · Host, memory and network

Windows Event Logs, Sysmon concepts, registry artefacts, Linux journal/authentication logs, Volatility 3, Wireshark, Zeek and timeline construction.

Practical: analyze self-generated logs or known training data and create a sourced timeline.

Month 4 · Reverse engineering

PE, ELF, Mach-O, DEX and APK structures; headers, sections, symbols, imports, disassembly, decompilation, control-flow and data-flow reasoning.

Practical: analyze a benign program you compiled, compare source to Ghidra output and parse a documented binary format.

Month 5 · Mobile and app security

Android manifests, permissions, exported components, signing, DEX, JADX/APKTool/Androguard/MobSF, OWASP WSTG/ASVS, secure code review and dependency analysis.

Practical: inventory an app you own, scan a repository you control, fix a lab weakness and retest.

Month 6 · Capstone and reporting

Complete one data-recovery lab, one reverse-engineering case and one defensive-security assessment using only authorized test material.

Deliver: hashes, tool versions, repeatable methods, findings, limitations, evidence references, remediation and a sanitized report.

A portfolio case is complete only when another analyst can understand the scope, reproduce the observations, identify the source evidence and see the limits of the conclusion.

Digital evidence and data-recovery playbook

Recovery is a preservation and analysis process—not a promise that deleted or damaged data can always be restored. Results depend on media condition, encryption, overwritten blocks, SSD TRIM, controller behaviour and acquisition quality.

1. Intake and authority

  • Confirm ownership or lawful authority to request the work.
  • Write down device, volume, account, data type, date range and exclusions.
  • Record make/model, serial number, capacity, physical condition and handover details.
  • Ask what happened and record previous repairs, recovery attempts or power-on attempts.
  • Agree handling, confidentiality, retention, return/disposal and cost before work begins.

2. Preserve the source

  • Stop unnecessary writes and do not install recovery software onto the source device.
  • For physical media, use appropriate write-blocking and a controlled acquisition workstation.
  • For unstable drives, use a qualified imaging workflow with a resumable map file; do not repeatedly power-cycle failing hardware.
  • Record tool version, settings, errors, start/end times and time zone.
  • Calculate SHA-256 hashes and preserve the original acquisition record.

3. Analyze a working copy

  • Identify partition and file-system structures before attempting recovery.
  • Prefer file-system-aware recovery where metadata remains available.
  • Use file carving only when necessary; it may lose names, folders and timestamps.
  • Validate recovered files by type, size, opening behaviour and hash; classify as complete, partial, fragment, corrupt or not verified.
  • Document what was not recoverable and any alternative explanation.
Never run repair tools on the original evidence source. Hash equality confirms bytes match between observations; it does not prove authenticity, ownership or chain-of-custody completeness.

Software reverse-engineering playbook

01

Establish provenance

Record authorization, source location, acquisition time, file size and SHA-256. Work on a copy and retain the original unchanged.

02

Identify the format and architecture

Start with magic bytes and metadata. Distinguish PE, ELF, Mach-O, DEX, APK and WebAssembly; extension alone is not proof of format.

03

Review structural metadata

Inspect headers, sections/segments, imports/exports, symbols, permissions, signing information and relevant manifest data.

04

Reason about code

Use disassembly, decompilation, cross-references and control-flow graphs. Treat decompiler output as an interpretation, not original source code.

05

Use dynamic analysis only in a lab

Run only known benign or authorized samples in isolated, snapshotted environments with controlled networking and no personal credentials.

06

Report evidence and uncertainty

Separate observed facts from hypotheses; cite offsets, functions, strings, hashes, tool versions and limitations. Do not infer maliciousness from entropy alone.

Android APK review can inventory the manifest, permissions, DEX files and native libraries. This is static app analysis; it is not acquisition of the phone owner's private data and does not bypass device encryption or operating-system controls.

Defensive application-security validation

Scope first

Identify assets, test accounts, permitted methods, time window, exclusions, emergency contact and change controls. Written authorization must cover each system and provider.

Review code and dependencies

Use static analysis, dependency checks and configuration review against repositories you control. Pin versions and preserve tool output.

Test safely

Prefer local labs or approved staging. Start with passive checks; avoid destructive tests, denial of service, data extraction, persistence or control bypass.

Validate every finding

Reproduce the observation, confirm affected component and impact, distinguish false positives, and use CWE/CVSS where appropriate.

Remediate and retest

Provide a specific fix, owner, priority and verification criteria. Record the retest evidence rather than relying on an assertion that the issue is fixed.

Protect client data

Redact credentials, tokens, keys and personal data. Do not put client data in public repositories or unapproved AI services.

A scanner result is a lead, not automatically a confirmed exploitable vulnerability. Validate it safely before describing it as a finding.

Lab safety, privacy and engagement rules

Authorization

Analyze only devices, applications, accounts, networks and data that you own or are explicitly authorized to assess. Written scope should identify the target, permitted actions, timing, exclusions, emergency contact and data-handling requirements.

Safe lab setup

  • Use separate virtual machines for analysis, testing and everyday work.
  • Keep unknown binaries offline by default; disable shared folders and host credential access in malware-analysis VMs.
  • Use synthetic data, dedicated accounts, snapshots and network egress restrictions.
  • Record tools and versions; verify downloads; do not disable endpoint protection on a normal workstation to run a sample.

Evidence and privacy

  • Record source identity, condition, timestamps and time zone, collector, transfers, hashes, tool settings and evidence storage location.
  • Preserve originals and work from copies; retain an access log and retention deadline.
  • Collect only what the authorized scope requires; encrypt data and limit access to named personnel.
  • Redact personal information, credentials, tokens, private keys and confidential content from reports.

Stop conditions

Stop if ownership or authority is unclear, activity moves outside scope, a device may be damaged, testing causes an outage or privacy exposure, evidence integrity cannot be maintained, or a legal hold/criminal matter requires specialist handling.

RevelaAI Portable Field Kit · Windows and Linux

Version 0.2.0 is the local command-line companion to the browser workbench. The Windows x64 edition bundles an embedded Python 3.14.10 runtime; Linux currently uses a host Python 3.10+ installation. Core utilities use the Python standard library.

Prepare Windows

  1. Download the Windows x64 ZIP from the Field Workbench page.
  2. Extract it to a dedicated USB drive, preferably exFAT or NTFS.
  3. Open PowerShell in the extracted folder and run .\Start-RevelaAI.cmd or double-click the launcher.
  4. Keep sensitive case folders on an encrypted, access-controlled volume.

The packaged Windows runtime is embedded and does not include pip. The preparation workflow validates the official Python archive against its published SHA-256 before packaging.

Prepare Linux

  1. Extract the package on a Linux host with Python 3.10 or newer.
  2. Run chmod +x start-linux.sh.
  3. Start the kit with ./start-linux.sh.

The Linux source package is not a self-contained OS runtime; the compatible Python interpreter must already be installed.

Core commands

python -m revela_fieldkit case create --root cases --id CASE-001 --title "Training evidence triage"
python -m revela_fieldkit inventory --case cases/CASE-001 --source ./sample-data
python -m revela_fieldkit verify --case cases/CASE-001
python -m revela_fieldkit binary inspect ./sample-data/program.exe --hash
python -m revela_fieldkit custody verify --case cases/CASE-001
python -m revela_fieldkit secrets scan ./my-repository
python -m revela_fieldkit doctor
python -m revela_fieldkit knowledge search "deleted files timeline"
python -m revela_fieldkit report --case cases/CASE-001

Optional local AI

The optional ask command can connect only to a loopback Ollama service. Ollama and the model must be installed or downloaded separately; neither is bundled with the USB kit. Local AI output can be wrong and must never be treated as forensic evidence or an authoritative conclusion.

The Field Kit is not a complete offline copy of cloud RevelaAI. It does not execute inspected binaries, acquire physical disks, repair source media, run arbitrary-target network scans or bypass encryption. Inventory hashing is not forensic imaging. Entropy and signatures are triage hints, not a malware verdict.

Build and integrity notes

The Windows USB edition was packaged from the RevelaAI portable source snapshot 9c1e2f472e04b89bbdfe49480039547df640ddc1 (Field Kit v0.2.0). The corresponding automated build ran 17 unit tests against the embedded Windows runtime; all passed, including PE64/ELF64/APK parsing, custody-chain verification, tamper detection, evidence inventory/verification, secret redaction and loopback-only Ollama checks.

The portfolio deployment pipeline rebuilds the pinned Windows package and publishes the ZIP under this website's /downloads/ path. A SHA-256 checksum file is published beside the download. Verify the checksum after downloading, before copying the kit to a USB drive.

Jumuiya Shamba Hub · Engineering overview

Shamba is the agriculture and farm-operations hub within Jumuiya. It brings farmer onboarding, registered farms, crops, activities, harvest tracking, agricultural intelligence, weather and market snapshots, recommendations, alerts, farm-rights review and marketplace safety into one workspace.

System boundaries

  • Frontend: React/JSX and Tailwind CSS, with the Shamba dashboard shell and shared Jumuiya API client.
  • Backend: existing RevelaCode backend and Jumuiya Flask blueprints; the API root is /api/jumuiya and the Shamba base is /api/jumuiya/shamba.
  • Storage: MongoDB through the shared Jumuiya database/collection gateway. Browser and AI services do not connect directly to MongoDB.
  • Authentication: user identity is derived from the authenticated server session; administrator queues and decisions require backend-recognized admin roles.

Farmer and farm lifecycle

  1. A signed-in farmer submits a Shamba farmer profile.
  2. An authorized Shamba administrator approves, rejects with a note, or requests more information.
  3. Only a profile explicitly marked approved may create a farm under the repaired backend contract.
  4. Farm-rights review is a separate decision from farmer-profile approval.
  5. Protected farm operations remain blocked until the farm-rights status is verified.
  6. Eligible farms use crops, activities, harvests, recommendations, alerts, weather and marketplace features.
Important safeguards: platform review is not government land-title certification; location and currency are not proof of land rights; a soil image is not a laboratory measurement of pH, NPK, salinity or contaminants; and a quote request is not a confirmed service booking or payment.

The implementation notes distinguish existing API contracts from features dependent on provider configuration or deployment. A draft code change is not a production release; verify backend and frontend deployment status before treating a feature as live.
